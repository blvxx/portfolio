01 / Business model

One event stream.
Several reporting views.

Every subscription event stores the post-event MRR and plan. Window functions reconstruct historical state without hard-coding month-by-month totals.

REVENUE

MRR and ARR

Monthly recurring revenue, annualized run rate, active customers and subscriptions.

REVENUE MOVEMENTS

New, expansion, contraction, churn

Each movement is derived from the prior subscription state and grouped into a monthly bridge.

RETENTION

GRR, NRR and cohorts

Retention formulas exclude new MRR; cohorts follow monthly active customers after first activation.

SEGMENTATION

Channel and region

MRR and active-customer contribution by acquisition channel and geographic segment.

DATA QUALITY

Lifecycle constraints

Valid event transitions, plan-to-MRR consistency, unique subscription timestamps and customer ownership.

RECONCILIATION

MRR bridge control

The opening balance plus movements must exactly reconcile to month-end MRR within a one-cent tolerance.

02 / Revenue bridge

03 / SQL implementation

PostgreSQL, beyond
basic SELECTs.

The project is structured as schema, deterministic seed, reusable analytical marts, reporting queries and fail-fast quality checks.

Event-state reconstruction

ROW_NUMBER() selects the last known subscription event before each month boundary. generate_series() creates a complete reporting calendar.

Movement calculations

LAG() compares post-event MRR with the previous state to classify upgrades, downgrades and cancellations.

Event movement with LAG()

SELECT
  subscription_id,
  event_type,
  mrr_after,
  LAG(mrr_after) OVER (
    PARTITION BY subscription_id
    ORDER BY event_at, event_id
  ) AS previous_mrr
FROM bi_subscription_events;
