02 / Incident catalogue

Ten failure patterns

Filter by layer to explore representative checks and first diagnostic commands.

Service lifecycle

01. systemd restart loop

HIGH

Service stays inactive or restarts repeatedly after a deploy or configuration change.

systemctl status api.service
journalctl -u api.service --since "30 min ago"
Host capacity

02. Disk / inode pressure

CRITICAL

Writes fail even though the application process is still running. Disk and inode exhaustion are checked separately.

df -h
df -i
du -xhd1 /var 2>/dev/null | sort -h
Reverse proxy

03. Nginx 502 Bad Gateway

HIGH

Proxy cannot reach the upstream, often due to a failed service, wrong bind address or port mismatch.

nginx -t
ss -lntp
curl -sv http://127.0.0.1:8000/health
Request latency

04. Nginx 504 timeout

HIGH

Upstream responds too slowly. Inspect latency and dependency saturation before changing timeouts.

curl -w 'total=%{time_total}\n' -o /dev/null -sS URL
journalctl -u api.service --since "15 min ago"
Name resolution

05. DNS lookup failure

HIGH

Internal hostname does not resolve. Check resolver state and scope before changing records.

getent hosts payments.internal
resolvectl status
dig payments.internal
Transport security

06. Expired TLS certificate

CRITICAL

Certificate expired, chain is incomplete or the wrong certificate is served for SNI.

openssl s_client -connect host:443 -servername host
certbot certificates
Memory / cgroups

07. OOM kill

HIGH

Kernel or container kills a process under memory pressure. Distinguish host memory from cgroup limits.

free -h
vmstat 1 5
journalctl -k | grep -Ei 'oom|killed process'
PostgreSQL

08. Connection pool exhausted

HIGH

Requests time out while the database is reachable. Inspect sessions, long transactions and pool sizing.

SELECT state, count(*)
FROM pg_stat_activity GROUP BY state;
Filesystem access

09. Permission denied

NORMAL

Service user cannot read a file or traverse a parent directory. Avoid broad permission changes.

namei -l /srv/app/config.yml
id api-user
getfacl /srv/app/config.yml
Network listener

10. Port conflict / refused

HIGH

Expected process cannot bind or the client connects to the wrong interface/port.

ss -lntup
systemctl cat api.service
curl -sv http://127.0.0.1:8000/health

03 / Tooling evidence

Log triage with source-line evidence

The CLI accelerates first-pass classification; it is a heuristic aid, not a root-cause oracle.

log_triage.py · sample input
$ python scripts/log_triage.py sample-logs/system.log --format json

{
  "findings": [
    {
      "rule_id": "DNS_FAILURE",
      "severity": "HIGH",
      "source": "system.log",
      "line": 12,
      "message": "Temporary failure in name resolution",
      "next_check": "getent hosts; dig; inspect resolver"
    }
  ]
}

What makes the result useful?

  • Severity-ranked finding with a stable rule ID.
  • Exact source file and line number for traceability.
  • Next diagnostic step rather than an unsupported root-cause claim.
  • Text and JSON output for both people and automation.
  • Unit tests cover rule order, evidence, output and input errors.
